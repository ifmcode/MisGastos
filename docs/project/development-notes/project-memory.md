## Goal
Build a hybrid app between a personal expense manager and Splitwise - personal finances + shared expenses with multi-wallet/multi-currency, history, filters, transfers between wallets, groups/friends with settlements.

## Key Decisions
- No photo uploads initially (keep it simple)
- Firebase as backend (Auth + Firestore). Rules in `firestore.rules`; deployment pending
- Strict TypeScript
- Tests target coverage >= 90% (see testing guide)
- Money: decimal numbers rounded to 2 decimals (strict input validation), not integer cents, for MVP. Revisit when transactions/transfers are implemented
- Wallets persisted in the root `wallets` collection with `ownerId`; queried by owner and sorted client-side. Dashboard totals grouped by currency (no conversion in MVP). `archivedAt` marks soft-deleted wallets: they leave selectors, filters and totals but keep their history and stored names. Permanent deletion either reassigns movements to a compatible active wallet (same currency, atomic target balance) or keeps them under the virtual `walletId: "-1"` with `[Eliminada] <name>` labels; transfers orphan only the deleted side
- Transfers persisted in a dedicated root `transfers` collection with `ownerId`. Only same-currency wallets can be linked; balances update atomically with `runTransaction`. Transfers are editable and use soft delete (`deletedAt`) with atomic balance reversion; hard deletes are denied in rules
- Dashboard global totals only include wallets with `includeInTotal`; selecting a wallet always shows its real balance and flags whether it contributes to the global total
- Categories live in the root `categories` collection scoped by `ownerId`. Defaults are seeded lazily when the owner has none, using deterministic ids (`${ownerId}__${legacyId}`); deleting the last category re-seeds them on the next load. Deletion is hard and blocked while transactions use the category. Seeded defaults keep their old transaction ids in `legacyId`, and forms/filters resolve either id so existing movements are never rewritten. Category type is locked after creation. Transfers remain uncategorized.
- **Dates**: Shared date utilities live in `shared/utils/date.ts` (moved from the transactions feature) and calendar-grid helpers in `shared/utils/date-calendar.ts`. All date inputs use the shared `DateQuickSelector` (Hoy/Ayer chips, a calendar button contiguous to them, and manual fallback). Movement/transfer forms also show an `Último DD/MM` chip after a successful save in the current session; it is preselected for new records, hidden when it matches Hoy/Ayer and not shown in filters. The session value lives in `shared/utils/last-used-date-store.ts` (in memory, not persisted). iOS/Android use `@react-native-community/datetimepicker`; web uses a lightweight in-app calendar grid because that library has no web support.
- **Email verification**: unverified email/password accounts are blocked from private routes and redirected to `/verify-email`; Google and unknown-provider accounts keep access. The screen shows the registered email, an explicit resend (no automatic resend after failed logins), a manual refresh and controlled polling (10s, max 6). The first email is sent once after registration from the screen so errors render inline. Existing accounts can resend, verify or sign out. Provider detection uses Firebase `providerData`, with no Firestore migration. Auth state is shared through `AuthProvider`, which exposes `refreshUser` so `user.reload()` updates navigation.
- **Theming**: `AppThemeProvider` owns the effective color scheme. It follows the system scheme until the user changes the Settings toggle, then persists the manual `light`/`dark` override under `misgastos.theme.preference` in AsyncStorage. Screens and components consume `useAppColorScheme`, `useFormTheme` or `useThemeColor`; raw colours stay in `shared/constants/theme-tokens.ts` (and feature palettes only for brand colours). `useFormTheme` is the preferred token source for forms, cards, filters and modals because it also exposes danger/success surfaces and text tokens for both schemes.
- **Ticket workflow**: implementation plan §0 is the source of truth for the current and next ticket. Start by marking the ticket `🚧 In progress` and updating §0. When a ticket is fully done, tick all requirements/acceptance criteria, set `✅ Done (DD/MM/YYYY)`, rename the file and H1 with the `[DONE] ` prefix (keeping the ticket id), update the plan feature status + §8 phase checkbox + §0 next ticket, update the roadmap and add a session entry here.
- **Git**: Never commit automatically. Keep changes staged. Ask before creating a separate commit for unrelated changes.
- **Code size & composition**: Files target ≤150 lines, one component per file, one responsibility per function. Screens only orchestrate: header, list header, footers, states and modals are separate components; derived data lives in hooks/pure utils. Styles go to `features/<feature>/styles/<name>.styles.ts` (style files may exceed 150 lines) with shared tokens and reusable base+variant styles. See `docs/project/guidelines/architecture-and-solid.md` §5.1
- **Movement detail view**: Tapping a movement card opens `TransactionDetailModal` instead of the edit form. `useTransactionDetailDialog` stores the selected id and resolves it from the full live collection, so the view always uses fresh data and shows `TransactionDetailMissingState` when the movement disappears. The pencil delegates to `useTransactionFormDialog.openEdit`; the trash reuses `getDeleteTransactionConfirmation` + `ConfirmDialog` + `deleteTransaction`. Wallet labels resolve from all wallets first, then fall back to the stored `walletName`; archived wallets get `(archivada)` and deleted wallets keep their `[Eliminada]` prefix
- **Transfer history**: `/transfers` is a stack route outside the tabs, included in `PRIVATE_SEGMENTS` so it follows the same auth/verification guard. `useTransfers` still owns the data and `getTransferHistoryItems` only dedupes by id, drops `deletedAt` records and sorts with `sortTransfersByDate`. `TransferItem` resolves names through `getTransferWalletNames` (live wallet including archived, stored name, then `Cartera eliminada`). The transfer form modal, `useTransferFormDialog`, form defaults and delete confirmation live in `features/transfers` so the dashboard and history share one edit/delete flow; no new query or duplicate form
- **Wallet selector**: The movement form and both transfer selectors share `WalletChipSelector` (up to three chips, selected wallet first, plus a `+` chip) and `WalletPickerDialog` (**Seleccionar cartera**, read-only, no creation). `getWalletChips`/`COMPACT_WALLET_LIMIT` live in `features/wallets/utils/wallet-chips.ts`, mirroring the category chip model. `getActiveWallets` stays the only archived filter and the screens pass the whole list down. Missing-wallet bug: each tab owns its `useWallets` state, so `TransactionsScreen` and `DashboardScreen` now refresh wallets on focus; the wallet existed all along and no mapper/query change was needed
- **Category ordering**: `sortOrder` (ascending) is the only ordering source. `features/categories/utils/category-order.ts` owns `compareCategories` (explicit order, then legacy `createdAt`/`name`), `getNextSortOrder`, `renumberCategories`, `applyCategoryOrder` and `moveCategory`. The repository sorts once and every consumer keeps that order. The categories screen only offers **Gastos** and **Ingresos** and starts on **Gastos**; it reorders through labelled ↑/↓ controls, and a move swaps the category with the previous/next visible one so the other type keeps its relative position. `reorderCategories` ignores unknown/duplicate ids, appends missing categories, skips unchanged writes and persists with a `writeBatch`; the hook applies moves optimistically and rolls back on failure. New categories append with `sortOrder = max + 1`; defaults seed by index. `firestore.rules` needed no change because `type` is untouched
- **Home summary**: TICKET-027 removes the home wallet-card list but keeps the wallet filter, totals and quick transfer action. `useDashboardOverview` derives recent movements/transfers through `getRecentMovements`/`getRecentTransfers`, capped at 3 with `hasMore` flags. `DashboardOverviewScroll` owns the pull-to-refresh layout; `DashboardMovementsSection` and `DashboardTransfersSection` own independent loading/error/empty states. Navigation callbacks are created in `DashboardScreen` via `createDashboardNavigationActions`; sections never navigate directly
- **Wallet transfer entry**: the create action lives in `WalletsTransferActions`, a row above the wallet list built from `getWalletsQuickActions` (transfer first, history always). `useWalletsTransferAction` bundles `useTransfers` + `useTransferFormDialog`, and `onWalletsChanged` calls `wallets.refresh()` so balances and totals update without a loading swap. Transfer visibility uses the shared `canTransferBetweenWallets(activeWallets)` rule; the dashboard keeps `useTransferFormDialog` only for editing recent transfers, and its header takes just `greeting`
