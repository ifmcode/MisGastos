## Goal
Build a hybrid app between a personal expense manager and Splitwise - personal finances + shared expenses with multi-wallet/multi-currency, history, filters, transfers between wallets, groups/friends with settlements.

## Architecture
See `docs/project/guidelines/architecture-and-solid.md`. Migrate incrementally to feature-first + layered architecture.

## Key Decisions
- No photo uploads initially (keep it simple)
- Firebase as backend (Auth + Firestore). Rules in `firestore.rules`; deployment pending
- **Rules language**: `firestore.rules` is Firebase's CEL-derived rules language, not TypeScript — a function body is one `return` with one expression (no `if`/`else`, no second `return`, no locals or loops), so branch with `? :` and keep helpers small. `npx firebase deploy --only firestore:rules --dry-run` validates compilation before a deploy
- Strict TypeScript
- Tests target coverage >= 90% for business logic (services, repositories, schemas and utils), enforced in `jest.config.js`; screens, components, hooks and styles are excluded until a React renderer is added (see testing guide)
- Money: decimal numbers rounded to 2 decimals (strict input validation), not integer cents, for MVP. Revisit when transactions/transfers are implemented
- Wallets persisted in the root `wallets` collection with `ownerId`; queried by owner and sorted client-side. Dashboard totals grouped by currency (no conversion in MVP). `archivedAt` marks soft-deleted wallets: they leave selectors, filters and totals but keep their history and stored names. Permanent deletion either reassigns movements to a compatible active wallet (same currency, atomic target balance) or keeps them under the virtual `walletId: "-1"` with `[Eliminada] <name>` labels; transfers orphan only the deleted side
- Transfers persisted in a dedicated root `transfers` collection with `ownerId`. Only same-currency wallets can be linked; balances update atomically with `runTransaction`. Transfers are editable and use soft delete (`deletedAt`) with atomic balance reversion; hard deletes are denied in rules
- Dashboard global totals only include wallets with `includeInTotal`; selecting a wallet always shows its real balance and flags whether it contributes to the global total
- Categories live in the root `categories` collection scoped by `ownerId`. Defaults are seeded lazily when the owner has none, using deterministic ids (`${ownerId}__${legacyId}`); deleting the last category re-seeds them on the next load. Deletion is hard and blocked while transactions use the category. Seeded defaults keep their old transaction ids in `legacyId`, and forms/filters resolve either id so existing movements are never rewritten. Category type is locked after creation. Transfers remain uncategorized.
- **Dates**: Shared date utilities live in `shared/utils/date.ts` (moved from the transactions feature) and calendar-grid helpers in `shared/utils/date-calendar.ts`. All date inputs use the shared `DateQuickSelector` (Hoy/Ayer chips, a calendar button pinned at the right of a wrapping chip group, and no manual typing since TICKET-063). Movement/transfer forms also show an `Último DD/MM` chip after a successful save in the current session; it is preselected for new records, hidden when it matches Hoy/Ayer and not shown in filters. The session value lives in `shared/utils/last-used-date-store.ts` (in memory, not persisted). iOS/Android use `@react-native-community/datetimepicker`; web uses a lightweight in-app calendar grid because that library has no web support.
- **Email verification**: unverified email/password accounts are blocked from private routes and redirected to `/verify-email`; Google and unknown-provider accounts keep access. The screen shows the registered email, an explicit resend (no automatic resend after failed logins), a manual refresh and controlled polling (10s, max 6). The first email is sent once after registration from the screen so errors render inline. Existing accounts can resend, verify or sign out. Provider detection uses Firebase `providerData`, with no Firestore migration. Auth state is shared through `AuthProvider`, which exposes `refreshUser` so `user.reload()` updates navigation.

- **Offline-first (TICKET-023 spike, 14/11/2026)**: `expo-sqlite` + explicit schema/migrations is the local source of truth, isolated behind a `DatabasePort` with an in-memory adapter for Jest. Feature repositories get a local implementation that validates and writes record + balance effect in one SQLite transaction, then appends a **coalesced** outbox row (one per entity, `clientMutationId`, `baseRevision`, `localSnapshot`, `serverSnapshot`, `dependsOn`). A single ordered sync engine drains the queue through `RemoteMutationExecutor`; each Firestore `runTransaction` first checks `appliedMutations/{ownerId}__{clientMutationId}`, so replays are exactly-once. Reads: full pull on login/first start plus owner-scoped `onSnapshot` listeners; tombstones are pulled and filtered locally. Balances stay server-authoritative and the UI shows `serverBalance + pendingDelta` recomputed from the outbox with the same pure helpers as the online path (`getSignedTransactionAmount`, `applyTransferToBalances`, `roundMoney`). Multi-device edits are expected: `revision` mismatch stops the mutation and opens an explicit conflict UI (`REMOTE_CHANGED`, `DELETED_REMOTELY`, `WALLET_UNAVAILABLE`, `INSUFFICIENT_FUNDS`, `INVALID`); no last-write-wins on money. Transactions move to soft delete (`deletedAt`) and wallets keep `archivedAt`; permanent wallet deletion stays online-only. All local rows are scoped and purged by `ownerId` on logout/switch, with a warning if changes are pending. OS-level storage protection is the V1 encryption stance. Offline data is retained until logout/account switch or an explicit local purge. Shared expenses and settlements must be **append-only ledger entries** folded by a shared pure function so the social phase stays offline-compatible. Full design: `docs/project/development-notes/session-notes/2026-11-14-offline-first-architecture.md`
- **Local DB foundations (TICKET-023, 24/11/2026)**: `DatabasePort` is **row-oriented** (table + row/where/orderBy/limit), not an execute-SQL surface, because only that contract can be implemented by both the `expo-sqlite` adapter and the in-memory adapter, which keeps Jest native-free and the coverage gate meaningful. `seq` lives in an `outboxSeq(ownerId, nextSeq)` counter row instead of an autoincrement column: the queue deletes rows on success, so an autoincrement would not stay monotonic across a drained queue, and strict ordering is a product requirement. `outbox` carries an explicit `operation` column (`create | update | delete`) because the coalescing matrix is undefined without it, and coalescing is allowed only for `pending`/`failed` rows (`syncing` and `conflict` must stay immutable: the first may already be server-side, the second is user evidence). Every local write accepts an optional `tx` so Phase 4 can commit record + balance + outbox row in one transaction; writes run through `withExclusiveTransactionAsync`, which is unavailable on web and leaves the web adapter to be decided in Phase 7. DDL and `PRAGMA user_version` commit in the same transaction. Schema additions beyond ADR §4 (`outboxSeq`, `outbox.operation`, `conflicts(ownerId)`) and the `roundMoney`-bound deviation of the signed-amount helper are recorded in `session-notes/2026-11-24-offline-local-db-foundations.md`
- **Revision and soft delete (TICKET-023 second slice, 24/11/2026)**: `wallets`, `transactions`, `transfers` and `categories` share one optimistic-concurrency counter: a create writes `revision: 0`, every update writes recorded + 1 in the same write as `updatedAt`, and a missing value counts as 0 so legacy documents stay editable after the deploy (the first update writes 1; no blocking backfill). The rules enforce it (`isRevisionBump`/`isInitialRevision`) and deny hard deletes of transactions; a delete is `deletedAt` + revision + 1 with an exactly-once balance revert, and only the owning shared/group operation may revert and close a linked movement. `appliedMutations/{ownerId}__{clientMutationId}` is owner-only and append-only with a missing-marker `get`, as the exactly-once marker the sync executor will write in Phase 5. Client ids are optional in the create DTOs so the Phase 4 local write can choose the id. Full detail: `session-notes/2026-11-24-offline-revision-and-soft-delete.md`
- **Offline read cache and offline banner (TICKET-023 third slice, 24/11/2026)**: reads are **cache-first with a remote refresh** — `use-async-collection` paints the cached list first and replaces it with the remote result, keeps the cached data when the remote read fails (without an error) and keeps today's loading/error behaviour on a cold cache; a background refresh stays remote-only. - **Offline sync engine and exactly-once (TICKET-023 fifth slice, 26/11/2026)**: a `clientMutationId` identifies **one immutable outbox payload**, so coalescing always issues a new id — reusing it would let the server report a different payload as already applied and drop the edit after a lost ack. A `create` already attempted coalesces as `update` (or `delete`) because the first attempt may exist server-side, while before any attempt the plain matrix applies including create+delete cancellation. `appliedMutations/{ownerId}__{clientMutationId}` is written in the same `runTransaction` as the money change; a replay returns the stored record **and** its wallets without re-applying, updates/deletes compare `baseRevision` with the stored `revision`, and deleting an already soft-deleted record is an idempotent success. The engine is single-flight per account, pushes strictly by outbox `seq` (head-of-line blocking on purpose), reclaims `syncing` rows left by a crash, requeues `failed` rows only for a manual retry, pulls the three personal collections after the push (no `onSnapshot` yet) and records `lastPushAt`/`lastPullAt`/`lastFullSyncAt`/`lastErrorCode`. `serialized.database.ts` queues every local transaction process-wide, so user writes, cache mirrors and the engine cannot interleave. Transient Firestore codes pause the queue with exponential backoff (1 s→5 min ±20 % jitter); conflicts and permanent errors stop it until the user acts. Conflicts (`REMOTE_CHANGED`, `DELETED_REMOTELY`, `WALLET_UNAVAILABLE`, `INSUFFICIENT_FUNDS`, `INVALID`) are resolved atomically (record + outbox + conflict in one local transaction) with keep-mine/keep-remote plans; the view model resolves wallet names from the local cache with the id as fallback. `transactions`/`transfers` split reads into `list` + `get`, and a `get` on a missing document resolves to not-found (the same existence-oracle trade-off as `appliedMutations`) so a remote delete is distinguishable from `permission-denied`; the rules are **pending deployment**. Full detail: `session-notes/2026-11-26-offline-sync-engine.md`
- **Offline social movements (TICKET-023 sixth slice, 26/11/2026)**: social rows live in new tables keyed by `(ownerId, id)` and never by `id` alone, because a friendship, a group or a shared movement has the same document id in every participant's account and an id-only key would let one account's cache overwrite another's. The sync executor always calls the **linked** update/delete for a social movement: the server operation reads the stored link, so a stale local snapshot can never orphan or double-charge a wallet movement created on another device. An update snapshot therefore never carries the link id, and editing a record the other participant already soft-deleted stops as a conflict (`DELETED_REMOTELY`), not as a permanent `permission-denied`. Linked personal movements are not mirrored locally: the social record is readable offline and its wallet effect comes from the outbox pending delta, while the personal movement appears only after the push and the following pull. A settlement/group-settlement notification is stored in the outbox snapshot (the builder is not serializable) and replayed idempotently by the executor. Group creation, invitations, joining and friend management are **online-only** (agreed scope: movement parity is the phase-6 exit criterion). ## Business Rules
- **No photos initially**: no avatar/photo uploads; use initials/icons.
- **Multi-wallet**: every expense/income belongs to one wallet.
- **Own transfers**: they do not change the net global balance, only the per-wallet balances; same-currency wallets only in V1.
- **Shared expenses**: balances must be exact; avoid careless floats (use cents/integers or Decimal when the social slice starts).
- **Currency**: stored per wallet and per shared/group expense; the group `defaultCurrency` is only the default for new group expenses. Conversion is out of V1.
- **Timestamps**: `createdAt`/`updatedAt` use server timestamps or ISO dates.
- **Soft deletes**: prefer `deletedAt` over hard deletes for financial records.
